# 导入与转换标准

版本：1.1.0  
Owner：导入器团队

## 1. 独立导入器

- Shopify 导入器：识别 Shopify 证据、Shopify 路由和交互。
- 外网导入器：处理非 Shopify、非 Wix 的普通授权网站或版式学习。
- Wix 导入器：当前未实现，必须 fail closed。

三者只共享任务状态、统一中间模型、组件 schema、资源服务和验收门禁；不得共享会造成平台串线的平台探测和页面解释逻辑。

- `Majestic 验证网站` 是 Shopify 导入器的固定验收样本名称。
- `Coco 验证网站` 是外网导入器的固定验收样本名称。

## 2. 导入模式

### 自有/授权网站

可导入获授权的文字、图片、结构和交互；必须保存授权声明和资源来源元数据。

### 第三方版式学习

只提取结构、排列、组件类型和交互形态；替换品牌、logo、图片、文字和来源编号，不复制受保护内容。

## 3. 标准流程

1. 明确选择导入平台，禁止静默回退。
2. 保存原站标准答案：路由、DOM 语义、直接资源、计算样式、关键截图、交互前后状态。
3. 单独抓取并验证页头、页脚、菜单、logo、字体、公共 CSS/JS。
4. 先跑 8 类代表页面，1–2 路并发，连续三遍稳定后扩容。
5. 识别一个组件，映射成标准 section/block/settings。
6. 立即对比组件；不通过不得保存为正式组件。
7. 组装一页并立即验收一页。
8. 每个可见菜单、按钮、卡片、弹窗、抽屉和表单都实际点击，并比较结果形态和数据变化。
9. 页面通过后加入正式结果。
10. 全部完成后做桌面、手机、路由和交互全站回归。

## 4. 中间模型

每个识别单元保存：source locator、结构类型、文本、直接媒体 URL、固有尺寸、容器尺寸、布局、交互触发、交互结果类型、目标路由、响应式状态、映射的 component type、settings、置信度和证据。

低置信度不得猜测为通过；进入人工复核或受控 fallback。

## 5. 任务状态和熔断

状态：未开始、等待公共资源、处理中、网络暂缓、内容失败、交互失败、已生成、已验收。

- 连续 3 个页面同类网络错误停止批次。
- 10 个页面网络失败超过 20% 停止批次。
- 公共资源失败停止所有依赖页面。
- 并发按 2→3→4 增长，失败率上升自动降级。
- 中断后只继续未完成或可重试项，不重做已验收页面。

## 6. 路由与交互

- 所有内部目标必须转换成本站路由且目标真实生成。
- 原站外链只有在产品策略允许时保留并明确标识。
- 原站是抽屉、弹窗、页内展开或局部刷新时，本地必须保持同类结果，不能仅生成独立页面。
- 产品详情、分类、搜索、登录、购物车、Quick Add 等状态必须走本平台合同。

## 7. 导入门禁

固定整页宽度、页面矩形截图冒充图片、菜单图包含页面壳、外链逃逸、缺失目标页、交互形态错误、硬编码不可编辑内容、平台误识别、代表样本未三遍通过，均直接失败。

## 8. 统一中间模型

```json
{
  "source": {
    "platform": "shopify|external-web|wix",
    "url": "https://example.com/path",
    "mode": "authorized|layout-learning"
  },
  "node": {
    "sourceId": "stable-capture-id",
    "kind": "section|block|text|image|video|control",
    "content": {},
    "layout": {},
    "responsive": {},
    "interaction": {
      "trigger": "click",
      "resultType": "route|drawer|modal|expand|mutation",
      "target": "/local-route"
    }
  },
  "mapping": {
    "componentKind": "section",
    "canonicalTypeKey": "hero-banner",
    "familyId": null,
    "componentTypeId": null,
    "settings": {},
    "confidence": 0.98,
    "evidenceIds": []
  }
}
```

`platform` 必须由显式选择和探测证据共同确认；冲突时返回 `PLATFORM_MISMATCH`。`confidence` 低于批准门槛时返回 `REVIEW_REQUIRED`，不能静默套用通用组件。

## 9. 导入任务清单

每个 route/component/action 有独立 task ID、依赖、attempt、错误类别、证据和 checkpoint。标准错误：`NETWORK_TRANSIENT`、`SOURCE_RATE_LIMITED`、`PUBLIC_ASSET_FAILED`、`CONTENT_MISMATCH`、`INTERACTION_MISMATCH`、`TARGET_ROUTE_MISSING`、`EXTERNAL_ESCAPE`、`SCHEMA_MAPPING_FAILED`。

## 10. 最终身份、命名和组件库合同

本标准必须与 `09-最终导入底层执行标准.md` 同时执行：

- 页面分别保存 `sourcePageId`、导入临时数字 ID 和平台页面数字 ID；来源没有编号时 `sourcePageId` 留空。
- 同一页面重导复用原平台页面数字 ID，URL、名称和来源编号不得充当平台 ID。
- 每个组件先做来源名称与实际功能核对，匹配才复用；缺失、宽泛或不匹配时按真实功能命名并保存证据。
- 每个组件必须保存 `componentKind`，生成带算法版本的三指纹，并提交完整的功能、数据、结构、交互、schema 和响应式合同。
- 分类只允许 `duplicate|preset|new-component|new-family|review-required`；section 与 theme block 禁止跨层级比较。
- 导入器只提交候选组件。Coco 全站验收和家族清单确认前，中心组件库状态必须为 `coco-v1-pending`，只保存候选、证据和审核队列，禁止分配正式 `familyId` 或 `componentTypeId`。
- Coco V1 确认后，中心组件库按稳定清单原子分配 `familyId`、`componentTypeId` 和 `presetId`；不得按爬取、DOM 或并发完成顺序编号。
- 旧纯数字 `platformComponentId` 只迁移为 `legacyPlatformComponentId` 历史别名，不能继续作为正式主键。
- 固定顺序为：公共资源 -> 页面身份 -> 名称核对 -> schema/settings -> 三指纹 -> 逐块验收 -> 原子保存 -> 整页验收 -> 全站验收。
