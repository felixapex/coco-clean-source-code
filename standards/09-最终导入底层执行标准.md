# 最终导入底层执行标准

版本：1.1.0

状态：canonical-current

本文件是 Shopify 导入器、外网导入器、未来 Wix 导入器以及后续渠道的共同底层合同。各渠道的识别、抓取和平台特有解析保持独立；只共享页面身份、组件命名、可编辑数据、组件库去重和自动验收合同。

## 1. 不可变执行顺序

1. 用户选择渠道；系统只进入对应导入器，禁止静默回退到另一导入器。
2. 保存原网站标准答案：公共资源、页面结构、文字、图片、尺寸、响应式状态和每个可见交互的实际结果。
3. 公共资源验收：页头、页脚、Logo、字体、菜单图片、公共脚本和样式未通过时禁止开始依赖页面。
4. 生成一个组件/页面之前先建立页面身份和来源证据。
5. 读取来源组件名称并执行“来源名称与实际功能核对”。
6. 名称匹配则复用来源名称；缺失、宽泛或不匹配时按实际区域和功能生成规范名称，并保存改名原因和证据。
7. 把文字、图片、视频、链接、字体、字号、字重、行高、字距、颜色、对齐、间距、圆角、比例、焦点、按钮样式、显示条件和内容来源抽成 schema/settings；不得把商家内容写死在 HTML。
8. 保存 `componentKind`，计算带算法版本的三指纹和硬合同，判定 `duplicate|preset|new-component|new-family|review-required`。
9. 生成一个组件/页面，立即执行逐块验收；通过才原子保存，失败不得进入正式结果。
10. 组装页面后执行整页验收；全部页面完成后执行全站验收。
11. 只有公共资源、组件、页面、全站四层门禁全部通过，才允许登记为唯一主版本。

## 2. 三层页面身份

每个页面必须同时支持三个互不替代的字段：

- `sourcePageId`：原网站明确提供的页面编号；原站没有时为 `null`，不得用 URL 冒充。
- `importPageId`：单次导入任务中的临时纯数字 ID，用于任务、证据和恢复点关联；不同导入任务可以变化。
- `platformPageId`：本平台永久纯数字 ID；页面首次进入平台时生成，以后同一页面重导复用，禁止重新生成。

`platformPageId` 在接口和 JSON 中按数字字符串保存，避免超过 JavaScript 安全整数后丢失精度。

辅助字段至少包含：`platform`、`sourceUrl`、`sourcePageName`、`canonicalRoute`、`identityKey`、`firstImportedAt`、`lastImportedAt`。URL、页面名称和来源编号分别保存，不能拿任何一个代替 `platformPageId`。

同一页面的身份优先使用 `platform + sourcePageId`；没有来源 ID 时使用 `platform + 规范化来源 URL`。URL 规范化必须消除无意义的尾斜杠、跟踪查询参数和大小写差异，但不能把不同产品、不同语言或不同页面错误合并。身份冲突必须返回 `PAGE_IDENTITY_CONFLICT`，不能覆盖旧页面。

## 3. 组件来源名称与实际功能

每个组件必须保存：

- `sourceComponentName`：原网站可观察到的原始名称；没有时为 `null`。
- `actualFunctionName`：根据页面真实功能得到的中文功能名。
- `normalizedComponentType`：供代码和组件库使用的英文 kebab-case 类型 ID。
- `nameMatchStatus`：`matched|missing|generic|mismatched|review-required`。
- `nameDecisionEvidence`：名称、DOM、文字、媒体、交互结果和截图证据 ID。

规则：

- `matched`：来源名称明确且和实际功能一致，复用来源名称。
- `missing`：来源没有名称，按实际功能命名。
- `generic`：来源只叫 section、block、container 等无功能含义的名字，按实际功能命名。
- `mismatched`：来源名称和页面功能不一致，按实际功能命名并保留原名。
- `review-required`：证据不足或一个区域混合多个核心功能，禁止自动进入正式组件库。

Shopify、外网、Wix 和未来渠道都执行同一核对规则；但平台证据的提取实现保持独立。

## 4. 组件正式档案

候选组件与正式组件必须分离：导入器只能提交候选组件，不能自行决定最终编号。中心组件库负责跨网站比较、家族归类、去重、预设、版本、来源登记和永久编号。

- `componentKind`：只允许 `section|theme-block`；不同层级不得判重或直接替换。
- `familyId`：四位数字字符串，例如 `0001`，表示语义功能家族，不表示页面顺序或像素坐标。
- `componentTypeId`：`familyId` 加家族内四位流水号，例如 `0001-0001`，表示正式组件能力合同。
- `canonicalTypeKey`：稳定英文 kebab-case 类型键，例如 `hero-banner`；不承担正式编号职责。
- `presetId`：同一组件默认 settings/blocks/布局组合，例如 `0001-0001-P001`。
- `componentVersion`：同一组件实现和 schema 的向后兼容版本。
- `componentInstanceId`：组件在某个页面中使用一次的实例 ID。
- `legacyPlatformComponentId`：旧纯数字组件 ID 的迁移别名，只用于历史查询，不能继续承担正式主键。

`familyId`、`componentTypeId` 和 `presetId` 必须按字符串保存，前导零是身份的一部分。相同组件只保存一份公共实现；网站和页面只保存正式组件类型、实例、顺序、settings/blocks 与来源关系。

每个候选组件至少保存：

1. `componentKind`、候选 `familyId/componentTypeId/presetId`（正式登记前允许为 `null`）。
2. `canonicalTypeKey`、`componentVersion`、`componentInstanceId`。
3. `sourceComponentName`、`sourceComponentId`、`actualFunctionName`。
4. `nameMatchStatus` 和 `nameDecisionEvidence`。
5. `schema`：settings、blocks、presets、使用范围、数量限制和数据合同。
6. `functionFingerprint`、`structureInteractionFingerprint`、`responsiveFingerprint` 及算法版本。
7. `classification`：`duplicate|preset|new-component|new-family|review-required`。
8. `sourceEvidence`：平台、页面、URL、DOM、截图、交互和网络证据。
9. 父子关系、排序位置、settings/blocks 值和替换兼容信息。

来源实例 ID 只作证据，不得直接充当本平台组件类型 ID。用户可修改的显示名称只用于界面展示，不参与身份或判重。

## 5. 三指纹和组件库判定

### 5.1 `functionFingerprint`

由组件核心用途和能力集合计算，例如横幅、轮播、翻页、自动播放、导航、表单、加购、筛选、抽屉。文字内容和品牌名称不参与功能指纹。

### 5.2 `structureInteractionFingerprint`

由语义结构、子组件顺序、控件种类、状态机、点击结果类型、键盘行为和本站路由目标计算。视觉相似但点击结果不同必须得到不同指纹。

### 5.3 `responsiveFingerprint`

由宽高比例、容器规则、列数变化、断点行为、元素显隐、顺序变化、裁切方式和手机布局计算。禁止使用单一固定像素宽度代表响应式规则。

### 5.4 分类规则

- `duplicate`：component kind、能力、数据、结构、交互、schema 和响应式合同等价，复用已有正式组件，只登记新来源和实例。
- `preset`：同一实现和能力合同，仅默认 settings、blocks 或可配置布局组合不同，新增 preset。
- `new-component`：同一家族，但存在现有 settings/preset 无法表达的结构、功能、数据、交互或响应式能力，新增家族内组件。
- `new-family`：不存在合适的语义功能家族，新增家族。
- `review-required`：证据不足、指纹冲突或相似度处于灰区，禁止自动合并和自动正式编号。

同一实现增加向后兼容 setting、修复渲染或升级 schema，且旧实例有明确迁移时，增加 `componentVersion`，不创建新组件。旧 `variant` 必须迁移成 preset、version 或 new-component；旧 `new` 必须拆成 new-component 或 new-family。

三指纹是带算法版本的证据。不得只靠截图相似度、CSS 类名、来源实例 ID、组件名称或图片比例判重，也不得越过 component kind、数据合同、schema 和交互硬门禁。

### 5.5 Coco V1 分配门禁

- Coco 全站四层验收和候选组件盘点完成前，中心组件库状态固定为 `coco-v1-pending`。
- `coco-v1-pending` 只允许保存候选、证据和审核队列，禁止分配正式 `familyId`、`componentTypeId` 或 `presetId`。
- Coco 内部归并后先产生稳定清单；用户确认后按清单固定顺序原子分配编号。不得按爬取、DOM、页面顺序或并发完成顺序编号。
- V1 固定后，后续网站只能复用、增加 preset、增加组件或增加家族，禁止重写已有身份。
- 旧登记器如果仍尝试生成纯数字组件 ID，必须 fail closed。

中心组件库固定处理顺序：`接收候选 -> 检查证据和 component kind -> 查询持久组件库 -> 五类判定 -> V1 门禁 -> 原子登记来源/实例/版本/预设 -> 保存可追溯决定`。第 11 个网站查询前 10 个网站累积的持久库，不依赖聊天记录或代理记忆。

### 5.6 旧字段迁移

- 旧 `platformComponentId` 改存为 `legacyPlatformComponentId`。
- 旧英文 `componentTypeId` 改存为 `canonicalTypeKey`。
- 切换正式主键前必须建立旧 ID 到新 ID 的一对一映射，并验证所有页面实例、来源、settings/blocks 引用。
- 任一旧引用无法解析时停止并回滚，禁止半套旧主键与半套新主键同时生效。

## 6. 逐块自验和保存事务

固定闭环：

`抓取标准答案 -> 生成一个组件/页面 -> 原站与本地逐块对比 -> 检查文字、图片、尺寸、自适应 -> 逐按钮点击并比较结果 -> 检查本站路由和目标页面 -> 检查 schema 与可编辑性 -> 通过才标记已验收 -> 原子保存 -> 再做下一块 -> 整页验收 -> 全站验收`

逐块验收必须比较：

- 文字内容、层级、字体、字号、字重、行高、字距、颜色和对齐。
- 图片/视频来源、宽高比、裁切、焦点、清晰度和加载状态。
- 宽度、高度、间距、列数、顺序、响应式变化、右侧留白、溢出、遮挡和重叠。
- 所有可见菜单、链接、按钮、输入和关闭控件的实际点击结果。
- 点击结果形态：页面跳转、抽屉、弹窗、展开、轮播、局部状态或数据变更。
- 目标必须是本站路由且目标页面已生成；允许的外部业务链接必须显式列入白名单。
- schema 能覆盖可编辑内容，空值和错误值有受控行为。
- 原站存在手机基线时比较来源一致性；原站没有手机基线时，只执行本平台响应式门禁，禁止伪造来源手机截图或来源一致性结论。

组件边界必须满足：

- 组件只保存从自身开始标签到对应结束标签的内容，禁止把后续组件、页脚、全站脚本或页面尾部外壳吞入组件变体。
- 组件之间的保真连接内容和最后一个组件之后的页面外壳必须作为页面 composition 片段单独保存，并按原顺序组装。
- 空的布局占位、`clearfix`、无内容的内容区域、脚本和样式支持节点不得登记为业务组件，但必须保留在 composition 中以保证整页可精确还原。
- 自定义 HTML / 页面构建器容器只允许拆分其顶层功能区块，或具有明确 `*-page` 语义的页面级包装；已经具备独立功能语义的组件必须保持原子性，禁止把其内部 Logo、说明文字、额度文字、装饰遮罩等内容零件再次登记为独立组件。
- 每页必须同时通过组件边界检查和整页逐字节重组检查；只通过其中一项不得验收。

正式目录写入必须采用临时结果 + 校验 + 原子替换。失败结果保留证据，但不得覆盖上一次已验收版本。

## 7. 批处理、错误分类和恢复

错误分为：

- 网络错误：连接重置、超时、限流。
- 公共资源错误：页头、页脚、Logo、字体、菜单图片、公共脚本或样式失败。
- 页面/组件错误：内容、布局、交互、schema 或路由失败。

硬规则：

- 连续 3 个页面发生相同网络错误，立即熔断。
- 任意连续 10 页网络失败超过 20%，立即熔断。
- 公共资源失败一次，阻止所有依赖页面。
- 先用 1–2 路并发跑 8 类代表页面三遍；全部通过后才按 2 -> 3 -> 4 路逐级扩容。
- 每个页面/组件记录未开始、处理中、网络暂缓、等待公共资源、内容失败、交互失败、已验收状态。
- 中断后只恢复未完成和失败任务，不重做已经验收的任务。

## 8. 硬失败门禁

以下任一发生即失败：固定页面宽度、右侧空白、横向滚动、文字重叠、元素遮挡、关键图片使用页面矩形截图冒充、来源域名逃逸、目标页面未生成、按钮未点击、点击结果类型不一致、不可关闭抽屉/弹窗、schema 缺失、写死商家内容、ID 冲突、低证据自动合并、section/theme-block 跨层级合并、按抓取顺序编号、前导零丢失、V1 前分配正式组件编号、伪造来源手机基线、逐块未通过却进入正式结果。

95% 视觉分数只是附加指标，不能覆盖任何硬失败门禁。

## 9. 渠道边界

- Shopify 导入器：只处理 Shopify 证据、路由和平台结构。
- 外网导入器：处理已授权网站或版式学习模式，不调用 Shopify 私有假设。
- Wix 导入器：当前未实现，必须 fail closed。
- 手机端不是另一套内容数据；同一 schema/settings 通过响应式规则渲染，但必须单独验收手机交互和布局。

共享合同不得包含 Shopify/Wix/具体网站的选择器、抓取器或修复特例。

## 10. 浏览器安全

严禁启动 Microsoft Edge，包括 headless、CDP、测试、截图、审计和抓取。不得关闭、禁用、卸载、杀死或重配用户的个人 Edge。所有浏览器依赖工作只能使用已明确配置的隔离非 Edge 浏览器；当前项目使用隔离 Google Chrome。未配置时必须在创建进程前 fail closed。

## 11. 完成定义

代码写完、单元测试通过、首页截图相似或某个页面可打开，都不代表完成。完成必须同时满足：合同校验通过、逐块验收通过、整页验收通过、全站回归通过、桌面与手机通过、全部路由闭包、全部可见控件点击结果匹配、组件档案完整、Coco V1 家族清单经过确认、正式结果原子保存、唯一主版本索引可验证。
